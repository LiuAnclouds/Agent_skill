# article-note-mentor

## 概述

这个 skill 是论文深度笔记的唯一主入口。

它对外承担完整链路：

- 读取论文与现有笔记
- 固定五段式结构
- 写作与分模块深化
- 生成内部格式标注表
- 对飞书文档做原位终稿处理
- 留存 Markdown 与格式标注归档

这里不再把“内容写作”和“飞书终稿”拆成两个对外 skill。写作、深化、格式评论、飞书落地、归档都在同一条工作流里完成。飞书文档是主版本，本地 Markdown 是留存、回退和再加工底稿，不是独立于飞书之外的平行终稿。

## 适用场景

- 从 PDF、论文网页、现有草稿生成稳定的中文研究型笔记
- 对旧笔记做结构重构、内容加厚和风格统一
- 需要把前备知识写成进入 `Work` 的桥梁层，而不是简单背景补充
- 需要在写完内容后再明确生成一层格式决策，并把它落到飞书文档
- 需要保留 Markdown 归档和格式标注归档，方便回退、审查和二次编辑

## 非目标

这个 skill 默认不追求以下结果：

- 单纯堆字数的长文
- 用百科抄写替代与论文绑定的解释
- 把 `Work` 写成碎片化小标题堆叠
- 为了排版而改动论文事实、章节顺序或方法内容
- 把飞书终稿处理理解成“再写一版正文”

## 输出契约

- 主笔记文件使用 `.md`
- 顶层结构固定为：
  - `一、前言`
  - `二、前备知识`
  - `三、Question&Study`
  - `四、Work`
  - `五、Conclusion`
- `Work` 默认继续使用五个功能块：
  - `1. 规则`
  - `2. 方法论创新`
  - `3. 实验设计`
  - `4. 主结果`
  - `5. 补充分析`
- 编号体系固定为：
  - 顶层：中文序号
  - 次级：`1. / 2. / 3.`
  - 再次级：`1.1 / 1.2 / 1.3`
- 格式评论阶段固定生成两份归档：
  - `<note>.format-annotations.md`
  - `<note>.format-annotations.json`
- Feishu 验收阶段固定追加两份归档：
  - `<note>.feishu-audit.md`
  - `<note>.feishu-audit.json`
- 格式标注表字段固定为：
  - `位置`
  - `原文片段`
  - `建议动作`
  - `强度等级`
  - `作用说明`
  - `Feishu 落地样式`
- `建议动作` 只允许：
  - `bold`
  - `italic`
  - `inline_code`
  - `bullet_list`
  - `numbered_list`
  - `quote_block`
  - `table_candidate`
  - `highlight_color`
  - `tighten_spacing`
  - `preserve_spacing`
- 飞书文档是主版本；Markdown、格式标注和 backup 是留存层

## 核心写作原则

### 1. 长，不等于堆字数

目标是“凝练但厚实”的研究笔记，不是把一句话拆成很多句。优先增加的是定义、公式、设计因果、证据链和结论边界的密度，而不是重复同义句。

### 2. 深，不等于过度类比

默认采用垂直客观阐释。先讲它是什么、符号是什么、它在做什么、为什么这样设计、它在全文中的作用，再决定是否需要少量类比。类比只能辅助理解，不能替代正式解释。

### 3. 能展开解释的内容，默认优先展开

遇到定义、符号、公式、模块、实验协议、表格、附录补证和作者观察时，默认先问“这里还能解释什么”，而不是先问“这里能不能省掉”。只要能补出作用、证据、上下文关系或边界，就不应草率略过。

### 4. `Work` 永远是主体

`前备知识`、`Question&Study`、`Conclusion` 都不是独立平行区，而是围绕 `Work` 服务。前者负责消除进入 `Work` 的认知断层，中间负责把问题链压实，最后负责对 `Work` 形成稳定判断。

## 固定工作流

完整工作流固定为五阶段，不再拆独立 polish skill。

### 1. 论文读取与结构定稿

- 读取论文、PDF、附录、现有笔记和已有飞书文档
- 固定五段式顶层结构与 `Work` 的功能块骨架
- 识别哪些内容可保留、哪些地方偏薄、哪些地方风格跑偏

### 2. 内容写作与分模块深化

- 先写能站住的骨架，再按模块逐块深化
- 深化时默认回钩论文原文、前置知识、方法链、证据链
- 合并重复表述，压掉两三句小节，把离散内容并回厚主题块

### 3. 格式评论阶段

这一阶段不是“顺手排版”，而是从已经稳定的内容中抽取一层明确的格式决策。它必须回答哪些句子要加粗，哪些术语更适合斜体或行内代码，哪些地方应该改成普通分点，哪些应该改成 `1. 2. 3.` 的编号分点，哪些表格值得重建为飞书真实表格，哪些地方要加颜色，哪些空行应该删除，哪些留白必须保留。这里必须覆盖真正影响阅读速度和层次辨识的句子，尤其是总判断句、分段收束句、关键术语、比较标签、表格前后的分析句、公式后的解释句。不能把这一阶段做成“全篇到处加粗”的机械标记，也不能只标局部词汇而忽略整段节奏。格式评论和 `Work` 的关系尤其紧：`Work` 越厚、逻辑越密，这一层越需要明确哪里该显化、哪里该收敛、哪里该避免样式噪音。如果看到某一块已经出现多张表、连续公式、密集比较、或长段落中埋着最终判断，就说明这里还可以继续解释，也说明这里更值得做格式标注，而不是让信息继续平铺。

### 4. Feishu 原位终稿阶段

这一阶段内部固定拆成“落地子阶段 + 验收子阶段”，但对外仍然算第 4 阶段，不新增第二个 skill。推荐入口是 `finalize`，顺序固定为 `preview -> apply -> audit -> 安全补打 -> final preview`。这里的 `audit` 不是泛泛检查，而是逐条回看格式标注是否在飞书块树里按位置命中：`table_candidate` 不能因为文档别处有真实表格就算完成，必须在注释位置附近命中；`highlight_color` 不能只给标签上色，关键纠偏句、边界提醒句、Conclusion 收束句也要检查；`bullet_list / numbered_list / quote_block` 不只看文本里有没有 `•` 或 `1.`，还要看块类型是否真正落成列表或引用。写回前固定生成 backup；涉及表格重建或块类型替换时，必须遵守“先建后删，删失败就回滚”的安全路径，避免因为单次 API 失败破坏原文。终稿验收产物固定写入 `.feishu-audit.md/.json`，其中至少要说明位置、期望动作、当前飞书状态、问题类型、严重等级、证据、修复建议和可否自动修复。只有在 `final preview` 中 `candidate_updates = 0`，且剩余问题只属于明确声明的稳定非自动修复差异时，才算这一阶段真正完成。

### 5. Markdown 留存归档

- 保留主 Markdown 作为内容留存
- 保留格式标注 `.md/.json` 作为审查与回退材料
- 保留 preview/apply 报告与飞书 backup 作为终稿操作记录

## 各部分默认目标

### `一、前言`

默认包含：

- 标题、作者、机构
- 论文地址、本地文件、开源地址
- 会议或版本信息
- 一句话核心判断
- 论文定位
- 阅读主线

### `二、前备知识`

目标不是罗列背景，而是为进入 `Work` 建桥。这里必须优先写论文默认读者已经懂、但如果不讲清楚就会在方法、公式、实验或结果解释处卡住的知识。每个前备知识块默认按“这是什么 -> 原理 / 定义 / 定理 / 关键公式 -> 变量与术语解释 -> 直观含义 -> 在本文中的具体作用 -> 如果不懂它会卡在哪个 `Work` 模块”写成闭环。不能只写百科式背景，也不能只讲一个抽象原理却不回钩论文。这里与 `Work` 的关系必须可见：写完一个知识点后，读者应该知道它将在 `规则`、`方法论创新`、`实验设计`、`主结果` 或 `补充分析` 的哪一处被用上。如果某个知识点还只能停留在“概念上知道它是什么”，却说不出变量含义、论文里怎样调用它、遗漏它会造成什么理解断层，就说明这里还可以继续解释，不应提前收手。

### `三、Question&Study`

目标是把问题链写清楚，再进入技术正文。默认包含研究背景、比较缺口、研究动机、核心命题、方法主张、贡献性质和证据边界。

### `四、Work`

`Work` 是主干、主体和灵魂，必须是全文最长、最厚、最有解释力的部分。这里不是把论文拆成很多小标题后每块写两三句，而是要把每个功能块写成“定义 -> 机制或公式 -> 作用 -> 证据 -> 边界”的闭环推进。默认优先遵循论文本身的讲解顺序，但写法上要更紧凑、更垂直、更充实，优先把离散知识压回厚段，而不是不断新开标题。公式后必须跟解释，表格后必须跟分析，实验结果不能只报数，附录补证不能只作为附加材料散放在文末。`Work` 与前后文的关系也必须明确：前备知识负责为它搭桥，`Question&Study` 负责把它要解决的争议讲清楚，`Conclusion` 负责对它进行压缩和判断。如果某个模块还能补充变量释义、实验协议、公平性来源、结果支持的判断、尚未证明的边界或与前后文的因果关系，就说明这里仍有深化空间，不应因为担心篇幅而略写。

### `五、Conclusion`

默认不是简单重述，而是给出稳定最终判断。推荐保持：

1. 核心结论
2. 主要判断
3. 可借鉴点
4. 局限与改进
5. 全文概括

## Feishu 终稿边界

Feishu 终稿阶段固定遵守以下边界：

- 纠错、监督、回传和补打全部内置在主 skill 的 Feishu 阶段，不再新增独立 review / correct / polish skill
- 终稿闭环固定为 `preview -> apply -> audit -> 安全补打 -> final preview`
- 默认开启管道表格重建，但已有真实表格优先保留
- 只处理明显段内公式 `$...$`
- 空文本块只做保守收缩
- 强调强度采用明显强调，但颜色只允许服务于结构标签、边界提醒和关键判断，不允许整段刷色
- 列表、引用、表格和留白都要按“位置命中”验收，而不是只看文档里是否存在同类样式
- 不改论文事实
- 不改章节顺序
- 不重写方法内容
- 不把整篇内容重排成另一套结构

## 质量标准

一个合格的笔记至少应满足：

- 五段式结构稳定
- `前备知识` 明显在为 `Work` 铺路
- `Work` 明显是主体
- 五个 `Work` 功能块各自形成解释闭环
- 重要公式没有裸奔出现
- 重要表格后有分析
- 格式评论表不是空泛标记，而是真正反映阅读层次
- 飞书终稿只改样式落地，不越界改正文事实
- `final preview` 应该达到 `candidate_updates = 0`，或只剩明确声明不可自动修复的稳定残差
- Markdown、格式标注和 backup 可以支撑回退与复查
